## Feature 1: System Tray / Menu Bar Native Integration

### 1.1 Current State

OmniMon already registers a basic system tray via Tauri 2 (`lib.rs:356-373`):

```rust
TrayIconBuilder::new()
    .menu(&menu)                        // "Show Monitor" + "Quit OmniMon"
    .tooltip("OmniMon - System Monitor")
    .on_menu_event(/* show/quit */)
    .build(app)?;
```

The tray icon is static (`icons/icon.png`, `iconAsTemplate: true`). No live metrics are displayed — the tray only serves as a launcher.

### 1.2 Goal

Allow OmniMon to run as a **menu bar app** (macOS) or **tray app** (Windows/Linux) showing real-time CPU/RAM/Network mini-graphs **without opening the main window**. The user should be able to:

- See CPU %, RAM %, and net throughput at a glance in the tray tooltip or icon.
- Click the tray icon to open a compact popover panel (not the full window).
- Optionally hide the dock icon on macOS (LSUIElement-style background app).
- Right-click → full context menu: Show Monitor, Quick Kill Top Process, Quit.

### 1.3 Architecture

#### 1.3.1 Dynamic Tray Icon with Metrics Overlay

Tauri 2's `TrayIcon` supports `set_icon()` and `set_tooltip()` at runtime. The plan:

```
watcher thread (2s tick)
    │
    ├──► SystemState { cpu, ram, net_rx, net_tx }
    │
    └──► new IPC event: "tray://metrics-update"
              │
              ▼
         lib.rs: tray_update_handler()
              │
              ├── set_tooltip("CPU 23% │ RAM 68% │ ↓1.2MB/s ↑340KB/s")
              │
              └── set_icon(render_mini_icon(cpu_pct, ram_pct))
```

**Option A — Text tooltip only (simplest)**:
Update `set_tooltip()` every 2 seconds with formatted metrics text. Zero visual rendering cost. Works on all platforms immediately.

**Option B — Dynamic icon rendering (recommended)**:
Generate a small (22x22 on macOS, 16x16 on Windows) PNG in-memory showing a mini bar chart of CPU + RAM. Use the `tiny-skia` crate (already a transitive dependency of Tauri) or the `image` crate to rasterize.

```
┌──────────────────────┐
│  Icon Canvas (22x22) │
│  ┌───┐ ┌───┐        │
│  │CPU│ │RAM│         │
│  │▓▓▓│ │▓▓ │         │
│  │▓▓▓│ │▓▓ │         │
│  │▓▓▓│ │▓▓ │         │
│  └───┘ └───┘        │
└──────────────────────┘
```

Implementation path:

```rust
// crates/core/src/tray_icon.rs (new module)

use tiny_skia::{Pixmap, Paint, Rect, Transform};

pub fn render_tray_icon(cpu_pct: f32, ram_pct: f32, size: u32) -> Vec<u8> {
    let mut pixmap = Pixmap::new(size, size).unwrap();

    // CPU bar (left half, green→yellow→red based on %)
    let cpu_height = (cpu_pct / 100.0 * size as f32) as u32;
    draw_bar(&mut pixmap, 2, size - cpu_height, 8, cpu_height, cpu_color(cpu_pct));

    // RAM bar (right half)
    let ram_height = (ram_pct / 100.0 * size as f32) as u32;
    draw_bar(&mut pixmap, 12, size - ram_height, 8, ram_height, ram_color(ram_pct));

    pixmap.encode_png().unwrap()
}
```

#### 1.3.2 Tray Popover Panel (Compact Widget)

Instead of opening the full 1100x700 window, clicking the tray icon opens a small Tauri webview window anchored to the tray icon position.

**Tauri 2 approach** — create a second window defined in `tauri.conf.json`:

```jsonc
// tauri.conf.json → app.windows
{
  "label": "tray-panel",
  "title": "",
  "width": 320,
  "height": 280,
  "visible": false,
  "decorations": false,
  "alwaysOnTop": true,
  "skipTaskbar": true,
  "resizable": false,
  "transparent": true,
  "url": "/tray.html"         // separate lightweight page
}
```

On tray icon click:

```rust
.on_tray_icon_event(|tray, event| {
    if let TrayIconEvent::Click { position, .. } = event {
        if let Some(panel) = tray.app_handle().get_webview_window("tray-panel") {
            // Position panel below/above the tray icon
            let _ = panel.set_position(calculate_panel_position(position));
            let _ = panel.show();
            let _ = panel.set_focus();
        }
    }
})
```

The `tray.html` page loads a minimal Svelte component (`TrayPanel.svelte`) that:
- Subscribes to the same `get_metrics` IPC.
- Shows CPU/RAM/Net sparklines (last 30 data points = 1 minute of history).
- Shows top 5 processes by RAM.
- Has a "Kill Top" button and "Open Full Monitor" button.
- Auto-hides when it loses focus (via `blur` event → `panel.hide()`).

#### 1.3.3 macOS Background App Mode (Hide Dock Icon)

On macOS, setting `LSUIElement = true` in `Info.plist` hides the dock icon, making OmniMon a pure menu bar app. This should be a **user preference** (not always-on), toggled in Settings:

```rust
// Toggle at runtime via NSApplication API
#[cfg(target_os = "macos")]
fn set_dock_icon_visible(visible: bool) {
    use cocoa::appkit::{NSApplication, NSApplicationActivationPolicy};
    unsafe {
        let app = NSApplication::sharedApplication(nil);
        let policy = if visible {
            NSApplicationActivationPolicy::NSApplicationActivationPolicyRegular
        } else {
            NSApplicationActivationPolicy::NSApplicationActivationPolicyAccessory
        };
        app.setActivationPolicy_(policy);
    }
}
```

Alternatively, use Tauri's `tauri::ActivationPolicy::Accessory` in the builder if available.

#### 1.3.5 Platform Considerations

| Platform | Tray icon | Dynamic icon | Popover panel | Dock hiding |
|---|---|---|---|---|
| **macOS** | Native menu bar | `iconAsTemplate: true` requires monochrome; color icons need `iconAsTemplate: false` | Position via `tray_rect()` — anchor below menu bar | `LSUIElement` / `ActivationPolicy::Accessory` |
| **Windows** | System tray | Full color 16x16 ICO | Position via `GetCursorPos` + screen bounds | Already no dock; minimize to tray is default |
| **Linux** | AppIndicator / StatusNotifier | Depends on DE (GNOME/KDE) | GTK popup or separate window | No dock concept; already tray-only |

### 1.4 Technical Challenges

1. **macOS `iconAsTemplate` vs color icons**: Template icons are monochrome and adapt to light/dark menu bar. Color bar charts need `iconAsTemplate: false`, but then lose automatic dark mode adaptation. **Solution**: Detect menu bar appearance and render appropriate icon variant.

2. **Tray panel positioning**: macOS menu bar is at the top, Windows taskbar can be top/bottom/left/right. Must calculate panel position relative to tray icon bounds. Tauri 2 exposes `tray_rect()` on macOS but Windows requires `Shell_NotifyIconGetRect`.

3. **Memory overhead of second webview**: The tray panel is a full Chromium webview. On systems with <8GB RAM, this matters. **Mitigation**: Keep the panel HTML tiny (<5KB), destroy webview when hidden for >60s, recreate on demand.

4. **Sparkline history data**: The watcher currently overwrites state. Need a ring buffer (e.g., `VecDeque<SystemState>` with capacity 30) to keep 1 minute of history for sparklines.

5. **Multi-monitor DPI**: Tray icon size must respect HiDPI (2x on Retina). Render at physical pixel size, not logical.

## Feature 2: Local AI Support (Ollama / Llama.cpp)

### 2.1 Current State

`ai.rs` supports 4 cloud providers via a single `AiProvider` enum:

```rust
pub enum AiProvider { OpenRouter, OpenAI, Gemini, Anthropic }
```

Each provider has:
- A hardcoded HTTPS API URL (`api_url()`)
- A keyring service for API key storage (`keyring_service()`)
- A `send_with_retry()` HTTP pipeline with exponential backoff

The CSP in `tauri.conf.json` whitelists only those 4 domains. All HTTP calls go through `reqwest` in Rust (not the browser).

### 2.2 Goal

Allow users to connect a **local AI model** running via [Ollama](https://ollama.com) (default `http://localhost:11434`) or any OpenAI-compatible local server (llama.cpp, LM Studio, LocalAI, vLLM), achieving:

- **Zero cost**: No API key required, no cloud calls.
- **Maximum privacy**: Process data never leaves the machine.
- **Offline capability**: Works without internet.

### 2.3 Architecture

#### 2.3.1 Extending AiProvider

Add `Ollama` and `Custom` variants to the enum:

```rust
#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize)]
pub enum AiProvider {
    // Cloud providers (existing)
    OpenRouter,
    OpenAI,
    Gemini,
    Anthropic,

    // Local providers (new)
    Ollama,
    Custom,     // User-specified base URL
}
```

Key behavior differences for local providers:

| Aspect | Cloud | Ollama / Custom |
|---|---|---|
| API key | Required (keyring) | Optional (most local servers don't need one) |
| Base URL | Hardcoded per provider | User-configurable (`http://localhost:11434` default for Ollama) |
| API format | Provider-specific | OpenAI-compatible (`/v1/chat/completions`) |
| CSP | Whitelisted domains | `connect-src` needs `http://localhost:*` or user-specified host |
| Timeout | 30s | Configurable (local models can be slow: 60-120s for 7B on CPU) |
| Retry | Exponential backoff | Simpler retry (local errors are usually fatal, not rate-limits) |

#### 2.3.2 Configuration Model

Extend `AiProviderConfig` on the frontend and backend:

```typescript
// Frontend: src/lib/types.ts
interface AiProviderConfig {
  provider: string;       // "openrouter" | "openai" | ... | "ollama" | "custom"
  model: string;          // e.g., "llama3.2:3b", "mistral:7b"
  baseUrl?: string;       // Only for ollama/custom. Default: "http://localhost:11434"
  apiKey?: string;        // Optional for local providers
  timeoutSecs?: number;   // Default: 30 for cloud, 120 for local
}
```

```rust
// Backend: crates/core/src/ai.rs
impl AiProvider {
    pub fn api_url(&self) -> &'static str {
        match self {
            // ... existing ...
            AiProvider::Ollama => "http://localhost:11434/v1/chat/completions",
            AiProvider::Custom => "", // Provided at runtime
        }
    }

    pub fn requires_api_key(&self) -> bool {
        !matches!(self, AiProvider::Ollama | AiProvider::Custom)
    }

    pub fn default_timeout_secs(&self) -> u64 {
        match self {
            AiProvider::Ollama | AiProvider::Custom => 120,
            _ => 30,
        }
    }
}
```

#### 2.3.3 Ollama Integration Path

Ollama exposes an **OpenAI-compatible** endpoint at `/v1/chat/completions` (since Ollama 0.1.24+). This means the existing `analyze_with_ai()` and `analyze_context()` functions already handle the correct JSON format — they just need to:

1. Target `http://localhost:11434/v1/chat/completions` instead of a cloud URL.
2. Skip the `Authorization: Bearer` header (or send an empty one).
3. Use a longer timeout.

**Minimal code change in `ai.rs`**:

```rust
pub async fn analyze_with_ai(
    provider: AiProvider,
    model: &str,
    processes_json: &str,
    profile: &str,
    base_url: Option<&str>,       // NEW parameter
) -> Result<Vec<ProcessSuggestion>, Box<dyn Error + Send + Sync>> {

    // For local providers, API key is optional
    let api_key = if provider.requires_api_key() {
        get_api_key(provider)?
    } else {
        get_api_key(provider).unwrap_or_default()
    };

    let url = match provider {
        AiProvider::Custom => base_url
            .ok_or("Custom provider requires a base URL")?
            .to_string(),
        AiProvider::Ollama => base_url
            .unwrap_or("http://localhost:11434")
            .trim_end_matches('/')
            .to_string() + "/v1/chat/completions",
        _ => provider.api_url().to_string(),
    };

    let timeout = Duration::from_secs(provider.default_timeout_secs());
    let client = Client::builder().timeout(timeout).build()?;

    // ... rest of the function uses `url` and `client` ...
}
```

#### 2.3.4 Ollama Health Check & Model Discovery

Before sending analysis requests, OmniMon should verify Ollama is running and discover available models:

```rust
// crates/core/src/ai.rs — new functions

/// Check if Ollama is running and reachable.
pub async fn check_ollama_health(base_url: &str) -> Result<bool, Box<dyn Error + Send + Sync>> {
    let client = Client::builder()
        .timeout(Duration::from_secs(5))
        .build()?;
    let resp = client.get(format!("{}/api/tags", base_url.trim_end_matches('/'))).send().await?;
    Ok(resp.status().is_success())
}

/// List locally available Ollama models.
pub async fn list_ollama_models(base_url: &str) -> Result<Vec<String>, Box<dyn Error + Send + Sync>> {
    let client = Client::builder()
        .timeout(Duration::from_secs(5))
        .build()?;
    let resp = client
        .get(format!("{}/api/tags", base_url.trim_end_matches('/')))
        .send()
        .await?;
    let json: serde_json::Value = resp.json().await?;
    let models = json["models"]
        .as_array()
        .map(|arr| {
            arr.iter()
                .filter_map(|m| m["name"].as_str().map(String::from))
                .collect()
        })
        .unwrap_or_default();
    Ok(models)
}
```

The Content Security Policy must allow connections to localhost for Ollama. However, since all HTTP calls go through Rust's `reqwest` (not browser `fetch`), **no CSP change is needed**. CSP only applies to webview requests, and Tauri `invoke()` calls bypass CSP entirely.

### 2.4 Technical Challenges

1. **Ollama not installed / not running**: Must handle connection refused gracefully. Show a clear "Ollama not detected" message with install instructions, not a cryptic network error. The health check endpoint (`/api/tags`) should be polled on settings open, not on every analysis request.

2. **Local model performance**: A 7B model on CPU-only can take 30-60 seconds to respond. The UI must show a progress indicator and the timeout must be extended. Consider streaming responses via SSE (`/v1/chat/completions` with `stream: true`) for perceived speed.

3. **Model quality for structured output**: Small local models (1-3B parameters) are significantly worse at returning valid JSON arrays compared to GPT-4o or Claude. `parse_suggestions()` already strips markdown fencing, but local models may produce other formats. **Mitigation**: Add a `repair_json()` step that attempts to fix common errors (trailing commas, missing brackets) before `serde_json::from_str`. Consider using a simpler prompt format for local models.

4. **RAM competition**: OmniMon monitors system resources, but running a 7B model consumes 4-8 GB of RAM. OmniMon should detect if the user's system is memory-constrained (<8 GB free) and warn before running local AI analysis. Irony: the system monitor recommending to close processes while itself consuming significant resources.

5. **Breaking function signatures**: Adding `base_url: Option<&str>` to `analyze_with_ai()` and `analyze_context()` is a breaking change for `crates/cli/`. Must update all call sites. Consider wrapping the new parameters in an `AiConfig` struct to avoid future signature churn:

    ```rust
    pub struct AiConfig {
        pub provider: AiProvider,
        pub model: String,
        pub base_url: Option<String>,
        pub timeout_secs: Option<u64>,
    }
    ```

6. **API key validation for Ollama**: The current `validate_api_key()` makes a test request to the cloud provider. For Ollama, "validation" means checking if the model is pulled and loaded. Use `GET /api/show` with the model name to verify.

## Shared Infrastructure Changes

### 3.1 Watcher Ring Buffer

Both features need historical metrics. Replace the single `SystemState` snapshot with a ring buffer:

```rust
// crates/core/src/watcher.rs
use std::collections::VecDeque;

const HISTORY_CAPACITY: usize = 30;  // 30 ticks × 2s = 1 minute

static CACHED_HISTORY: OnceLock<Arc<RwLock<VecDeque<SystemState>>>> = OnceLock::new();

pub fn get_cached_state() -> SystemState {
    // Returns the latest entry (backwards compatible)
    let history = cached_history().read().unwrap();
    history.back().cloned().unwrap_or_default()
}

pub fn get_state_history() -> Vec<SystemState> {
    let history = cached_history().read().unwrap();
    history.iter().cloned().collect()
}
```

Avoid parameter sprawl by introducing a config struct used across all AI functions:

pub struct AiConfig {

## Característica 1: System Tray / Barra de Menú Nativa

### Resumen

Extender el ícono de bandeja existente (actualmente estático) para mostrar métricas en tiempo real (CPU, RAM, red) sin abrir la ventana principal. Incluye:

- **Tooltip dinámico**: Actualizado cada 2s con estadísticas del sistema.
- **Ícono dinámico**: Mini gráfico de barras CPU/RAM renderizado en Rust con `tiny-skia`.
- **Panel popover**: Ventana compacta (320x280) anclada al ícono de la bandeja con sparklines de 1 minuto y los top 5 procesos.
- **Modo background en macOS**: Opción de ocultar el ícono del dock (`LSUIElement`).

### Retos Técnicos

1. Los íconos template de macOS son monocromáticos — los gráficos de colores requieren detectar el tema de la barra de menú.
2. El posicionamiento del panel popover varía según la plataforma y la posición de la barra de tareas.
3. El costo en memoria del segundo webview (~30-50MB) puede ser significativo en sistemas con poca RAM.
4. Se necesita un buffer circular en el watcher para mantener historial de 1 minuto.

## Característica 2: Soporte de IA Local (Ollama / Llama.cpp)

### Resumen

Agregar `Ollama` y `Custom` como variantes de `AiProvider` para permitir análisis de procesos con modelos locales. Ollama expone un endpoint compatible con OpenAI (`/v1/chat/completions`), por lo que los cambios en `ai.rs` son mínimos:

- Nuevo parámetro `base_url` para URL configurable.
- Sin API key obligatorio para proveedores locales.
- Timeout extendido (120s vs 30s) para modelos locales.
- Health check (`/api/tags`) y listado de modelos disponibles.
- UI condicional en Settings: campos de Base URL y dropdown de modelos auto-populado.

### Retos Técnicos

1. Detectar graciosamente cuando Ollama no está instalado o no está corriendo.
2. Modelos locales pequeños (1-3B) generan JSON malformado con más frecuencia — necesitamos reparación de JSON.
3. Competencia de RAM: un modelo de 7B consume 4-8 GB — debemos advertir al usuario si el sistema está limitado.
4. El cambio de firma de `analyze_with_ai()` requiere actualizar todos los call sites en `crates/cli/`.
5. Streaming de respuestas (SSE) para mejor UX con modelos lentos es deseable pero agrega complejidad.
